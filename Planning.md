# Communication Coach Telegram Agent — Plan

## Context
- Source material: Plan.md (client transcript + siddhu's design notes), Video.md (Vinh Giang "30-Day Communication Mirror" plan analysis, PDF vs video comparison), Issues.md (a self-review pass flagging blockers/gaps against the plan as of the last round - this round's changes resolve or make explicit decisions on every item in it).
- Goal: Telegram chatbot that acts as an AI extension/coach of Vinh Giang's video, guiding a user through record -> 24h wait -> 3-day audit (auditory/visual/transcription) -> pick one habit -> weekly trigger+re-evaluation -> adaptive lifelong Kaizen loop.
- This is a POC/demo, not production. Workspace currently has only Plan.md, Video.md, and Issues.md - no code yet.

## Decisions from alignment questions
- Stack: Python, python-telegram-bot (async) - **standard cloud `api.telegram.org` endpoint, no local Bot API server needed** (reversed this round - see the Loom pivot below; the local server existed solely to download large videos, which is no longer required since the primary submission path is a Loom link + pasted transcript, and the fallback voice-note path is small enough for the default 20MB cloud download limit).
- LLM: **OpenAI-only for MVP** (revised in Phase 1 planning) - Whisper transcription requires OpenAI regardless, so a separate Anthropic integration adds cost/complexity without real benefit for a demo. `LLMClient` kept as a thin interface so an `AnthropicClient` could be added later without touching `agent_core`, but not implemented now. User has no OpenAI key yet - needs to obtain one before first run.
- Persistence: SQLite file via **`aiosqlite`** (async-safe wrapper, not blocking `sqlite3` - revised in Phase 2 planning since PTB is fully async), simple schema, no heavy ORM.
- **Media analysis scope - SUPERSEDED this round: Loom replaces the local-Bot-API-server/ffmpeg/Whisper video pipeline entirely** (research-backed pivot, confirmed via Loom's live pricing/docs and the user's own hands-on testing): the initial recording and every weekly check-in are now submitted as **a Loom share link + a pasted/uploaded transcript + an optional pasted/uploaded summary** ("2 files + link"), not a Telegram video upload. This removes the download-size problem, the Whisper file-size problem, and the `whisper-1` deprecation risk in one move, since no video ever needs to be downloaded or transcribed by the bot for the primary path. Confirmed via Loom's official pricing page (Sept 2026): the free **Starter** tier caps screen recordings at **5 minutes** but includes transcriptions in 50+ languages; **Business** ($18/user/mo) unlocks unlimited recording time; **filler-word removal is a paid Business+AI-only feature**, so default transcripts (Starter/Business) reliably retain filler words - matching the user's own direct testing.
- **Duration choice - both upfront and adaptive**: at onboarding/initial-recording, the agent explicitly asks whether the user can do the 20-minute "advanced" recording (needs Loom's paid Business tier for unlimited length) or should use the 5-minute "beginner" path (works on Loom's free Starter tier) - **and** separately, the agent always reads the actual duration back from Loom's oEmbed response after submission and adapts its framing to whatever was actually recorded, rather than treating a shorter-than-expected video as a failure. **Weekly check-ins have no hard duration target** - free-tier users are naturally capped at 5 minutes by Loom itself, users with the 20-minute capability may run longer if they want, but the plan never enforces either; the agent adapts to whatever comes back, consistent with the "adaptive planning, no rigid constraints" principle.
- **Submission format - `.txt` upload is the default, pasting is short-recording-only (REVISED after review caught a real message-size bug)**: a 20-minute transcript is roughly 3,000 words / ~18,000 characters - well over Telegram's **4,096-character single-message limit** - so "paste the transcript here" cannot work as the default instruction for anything beyond a few minutes of speech; even the 5-minute "beginner" path (~750 words / ~4,500 characters) is borderline over the limit. The agent's default instruction is now **always upload the transcript (and summary) as a `.txt` file** - Telegram documents have no such size problem, comfortably handling any transcript length via the standard cloud Bot API. Pasted text remains accepted for genuinely short content (under ~3,500 characters, leaving headroom), but if a pasted message looks truncated (ends abruptly, sits right at the length ceiling, or the user indicates there's more), **the agent explicitly asks whether there's more content and steers them toward `.txt` upload instead of attempting to silently reassemble multiple chunked messages** - no debounce/coalescing logic is built, since Telegram/mobile clients may auto-split a long paste into several messages with no reliable "this is the last chunk" signal, which the file-upload default sidesteps entirely. The Loom link, transcript file, and (optional) summary can still arrive in any order, across separate messages - it's specifically a single transcript payload that should be one file (or one short paste), never manually split by the user across many messages.
- **Loom's AI summary is optional supplementary context only, never used for metrics**: when the user provides it, the agent may fold it into the LLM's context as an extra qualitative signal (e.g., a quick sense of what was discussed) - it is never treated as an authoritative source for filler counts, WPM, or pause detection, and its absence never blocks progress (it's a paid Business+AI feature, not always available).
- **Fail-soft pause-metric estimation from Loom's transcript timestamps - math CORRECTED after review caught a self-cancelling bug**: the original design estimated silence as `gap - (word_count / overall_wpm)`, but `overall_wpm` is itself `total_words / oEmbed_duration`, and that duration already includes every pause in the recording - so summing the "expected spoken time" this formula predicts for every paragraph mathematically reconstructs the *total* duration exactly, meaning the residuals (the "silences") average to zero **by construction**, regardless of how much the person actually paused. This would produce roughly as many spurious negative "silences" as positive ones and systematically under-report `long_pause_count` no matter what. **Fix: use an articulation rate, not the overall rate** - compute each paragraph's own `words_i / duration_i` (its own words divided by the gap to the next timestamp), then take the **85th percentile across all paragraphs** as the estimated "pace while actually speaking, unpaused" baseline (self-calibrating per recording, since some paragraphs will happen to have little or no pause and represent the person's true articulation speed). Silence per paragraph is then `gap_i - (words_i / articulation_rate)` against *this* baseline, which is no longer guaranteed to cancel out. **Fallback**: if there are fewer than ~5 paragraphs (too few to take a stable percentile from), fall back to a literature-standard conversational rate constant (~150 wpm) as the articulation-rate baseline instead. If the pasted text's timestamp format doesn't match any recognized pattern (different desktop/mobile copy format, different language, or a summary-only paste), the parser **fails soft**: it does not throw or block the pipeline, it simply omits the two pause-metric `entry_metrics` rows for that entry (never writes a misleading `0`) while the other five metrics (filler count/rate, duration, WPM, repetition count) still compute normally from the raw transcript text plus oEmbed's reported duration, which don't need timestamps at all. **The agent tells the user transparently when this happens** ("couldn't estimate pauses from what you pasted, everything else came through fine") - consistent with the plan's "always show the mirror honestly" principle, never a silent omission.
- **Fallback path when Loom fails or the transcript is insufficient - user's choice each time, not a fixed mode**: if the user can't complete the Loom flow (no account, link/transcript won't work, technical issue), the agent offers a Telegram voice-message fallback and **explicitly lets the user choose, at that moment, between two sub-options**: (a) **self-report only** - no automatic transcription, the bot doesn't process the voice note's audio content at all, it just has a normal reflective conversation about how the practice went (same pattern as Day 2's muted self-report) and logs it qualitatively, with zero new infrastructure; or (b) **full metrics via a lightweight ASR call** - the bot downloads the small voice note (Telegram voice notes are OGG/Opus, typically 1-4MB even for 20 minutes, comfortably under the cloud Bot API's 20MB limit with no local server needed) and sends it to a transcription API to get real filler/WPM/duration numbers, at the cost of reintroducing a per-minute ASR charge and the `whisper-1` deprecation risk (Aug 2026 deprecated, Feb 2027 shutdown) - but now scoped to rare fallback occurrences only, not every submission. **A minimal format-conversion step (a lightweight `ffmpeg` call, not the old full video-extraction pipeline) may be needed** if Telegram's OGG/Opus voice-note container isn't directly accepted by the transcription API (OpenAI's supported input formats are `mp3, mp4, mpeg, mpga, m4a, wav, webm` - `ogg` is not listed), so this branch keeps a narrow, optional `ffmpeg` dependency rather than reintroducing the full Phase 0.5 pipeline. Both sub-options apply equally whether the failure happens on the initial recording or any weekly check-in.
- **Filler-word preservation - now confirmed via the user's own direct Loom testing, not solely a spike**: the user has personally confirmed that Loom transcripts on their account retain filler words and that copy-pasted timestamps survive per-paragraph. **Phase 0.5 is retained but substantially lighter** (see below) - it now validates the Loom-transcript-parsing path end-to-end (real recording -> real copy-paste -> parser) rather than testing an ASR provider's raw output, and only *optionally* stretch-tests the scoped-down voice-fallback ASR call if that branch is exercised.
- **Missed-day detection redefined** (Issues.md caught a false-positive bug): a "missed day" during `weekly_cycle` now means **no user engagement at all that day** (no incoming message from the user), not "exercise not marked completed." Vinh's real method for the weekly habit cycle is a passive trigger (phone wallpaper), not a daily assigned task, so checking for a completed exercise row would flag nearly every day as missed. See the new `daily_engagement` table (Phase 2) and Phase 4's revised step 1.
- **Weekly re-evaluation always surfaces the metric trend, never conditionally** (refines the "self-assessment is conclusive" principle after Issues.md flagged it could quietly defeat the whole "communication mirror" premise): the user's self-report is still elicited first, and their *interpretation* of what the numbers mean still wins (Principle 2's trust rule - never accuse of lying) - but the agent no longer skips showing the actual metric trend just because the user already reports feeling improved. The mirror itself is never optional; only the meaning assigned to it is user-led. See Phase 3's weekly re-evaluation E-P-E bullet.
- **Habit-transition/Day-30 comparison artifact** (new - closes a real gap Issues.md pointed out: there was previously no "measured improvement" deliverable at all): at the first habit-transition moment (and available on request thereafter), the agent composes a short, LLM-authored text comparison - baseline recording's metrics vs the latest, plus a callback to the user's own onboarding "5 words" - delivered alongside the existing lifelong-Kaizen reveal moment. See Phase 3.
- **No streaming - typing indicator + a complete message instead** (reverses the earlier "streaming from day 1" decision, after Issues.md argued progressive `edit_message_text` reads as visibly machine-like, not human, and is the fiddliest part of the build for a UX downgrade): `ChatAction.TYPING` is shown while the model composes a reply, then one complete message is sent (optionally split into two short bubbles with a brief delay for more human pacing, at `agent_core`'s discretion for longer replies). This also simplifies `LLMClient` - no `on_delta` callback, no delta-accumulation or tool-call-argument-index reconstruction, `stream=False` throughout. See Phase 1.
- MUST leave open ends for later "full analysis" (audio signal heuristics: pitch/pace/volume; visual heuristics: eye contact/gestures via vision model) - achieved via a `MediaAnalyzer` abstraction + always storing raw Telegram file references so old recordings can be reprocessed later without re-collecting data.
- **Time progression - canonical day resolver** (fixes a real bug Issues.md caught: `simulated_day` never advanced for a real, non-demo user, since only `/advance` ever touched it): see Phase 4's `get_effective_day()` design - real wall-clock time now advances a user's "day" automatically with zero explicit incrementing code, while `/advance` still works identically for demos.
- Hosting: local polling bot for demo - **no second local process needed** (reversed this round - the local Bot API server is no longer part of the design, see the Loom pivot above).
- Secrets hygiene: `DEMO_PASSCODE`, all API keys live only in `.env` (gitignored), never hardcoded or logged; `.env.example` ships with placeholder values only. **`TELEGRAM_LOCAL_API_ID`/`TELEGRAM_LOCAL_API_HASH` removed this round** - no longer needed without the local server.

## Behavioral principles to encode in system prompt (from Plan.md notes)
1. Agent's #1 aim: help the user succeed, at any cost - plan is always adaptable, never rigid.
2. Never assume the user is lying/dishonest about self-reported progress; ignorance != dishonesty. **The mirror (data/metrics) is still always shown neutrally regardless of self-report** (refined this round after Issues.md review) - trusting the user's sincerity is about how their *interpretation* is treated, never about hiding the numbers from them; see Phase 3's weekly re-evaluation note.
3. One habit/issue at a time - no parallel work streams.
4. User retains final say on **which habit to target and what specific exercise/trigger to use**, but the agent always leads by proposing 2-3 concrete, data-grounded options (not a rigid single "top pick" - presented neutrally, no hard default) at every decision point: habit selection after the audit, weekly exercise/trigger design within a habit, and adaptive replanning after missed days. User can pick one of the options or freely override with their own idea; the agent never proceeds without the user's explicit choice. Full plan is still never dumped all at once - revealed step-by-step through these suggestion exchanges. **Judgment-call note (Issues.md flagged this contradiction explicitly)**: this resolves a real tension between siddhu's original notes ("it should never suggest from up front... give full autonomy... never interfere") and the client's brief ("adaptive planning and proactive messages - that's basically what we need to build," reacting when the user misses days) in favor of the client's brief - documented here, and called out explicitly in the Loom/README judgment-calls writeup (see Phase 6), rather than left as a silent, unacknowledged contradiction between the source notes. **Scope-honesty note (the second, subtler version of this tension, per Issues.md)**: "the user has full autonomy over the plan" is false by construction - the overall framework (record -> 24h wait -> 3-day audit -> pick one habit -> weekly trigger+re-evaluation -> lifelong Kaizen loop) is Vinh's fixed structure, hardcoded into the agent, never something the user designs from scratch. What the user genuinely chooses, within that fixed structure, is *which* habit to target and *what* specific exercise/trigger to use each week - the system prompt and any user-facing framing state this honestly (e.g., "you decide what we work on and how, I'll hold you to Vinh's method for how we get there") rather than implying the user authors the whole journey.
5. Persona: warm, non-judgmental, "buddy"/coach tone, loosely borrowing Vinh Giang's voice/style from Video.md content (not impersonating him - "this is Vin's sidekick").
6. Detailed journal: log exercises assigned, completed/not completed + reason, audit notes, day-count per habit.
7. Adaptive follow-up, in strict order - **why before shrink** (refined after gap analysis against Plan.md's exact wording: "let's analyze why weren't you able to do this... if that was hard, let's start with something smaller"): if user misses ~2 sessions in a row or doesn't complete an exercise, the agent must first ask *why* with genuine, non-judgmental curiosity - never skip straight to offering a smaller/easier version. Only once the reason is understood does the agent offer to shrink scope / adjust plan, informed by that specific reason - never punitive, and never a shortcut around the curiosity step.
8. **Observer/mirror role** (grounded in Motivational Interviewing's OARS technique - Open questions, Affirmations, Reflective listening, Summaries): whenever the agent notices something worth surfacing (a pattern in a transcript, a recurring theme, a missed exercise, anything at all), it shares the observation neutrally as a reflection - it never asserts a diagnosis outright (e.g., "I noticed you used 'and' a lot", not "You have a filler-word problem"). **It then asks if the user agrees/recognizes it themselves first** ("Does that sound right to you?") - never assumes the observation is accurate or important to the user. Only once the user confirms does the agent continue exploring - why/how, and how long they've noticed this - as a genuine multi-turn back-and-forth, one question at a time, not a single bundled question-answer exchange. If the user disagrees or pushes back, the agent doesn't argue or insist (mirrors MI's "avoid arguments"/non-confrontational stance) - it accepts their perspective and either drops the observation or asks how they'd frame it instead. This is a continuous, standing behavior throughout every conversation, distinct from the suggestion-mechanics options in Principle 4. **Named anti-pattern to explicitly avoid throughout: MI's "righting reflex"** - the counselor's urge to jump in with unsolicited advice, corrections, or fixes before the user has had a chance to arrive at the insight or decision themselves. The agent's system prompt names this pattern explicitly.
9. **Affirmation before gaps - personalized, not generic** (refined after gap analysis + research into MI's "affirmation" component and growth-mindset praise research): whenever reviewing progress of any kind - weekly re-evaluation, adaptive replanning after missed days, the Day-3 audit, or any moment looking back at what happened - the agent first explicitly affirms real effort, partial progress, or past success, before discussing gaps or what still needs work. It never opens a progress review by leading with what went wrong. **Generic/canned praise ("Great job!", "Well done!") is never used alone** - the agent instead picks the affirmation *lens* that fits the moment, and phrases it using specifics from what actually happened or the user's own words wherever possible:
   - **Effort/process praise** (grounded in growth-mindset research - Dweck: praising effort/strategy/persistence builds resilience better than praising fixed traits, especially after a setback): the default lens for anything about trying, practicing, or showing up - e.g., "you kept at this even though the week got hectic," not "you're a natural."
   - **Self-efficacy praise** (grounded in MI's self-efficacy-building technique of reflecting the client's own precedent back to them): draws on a past success or strength the *user themselves* previously described and reflects it back - "you've done hard things like this before, like when you..." - used before a new commitment or decision point.
   - **Identity/values praise**: ties the specific progress being reviewed back to the user's own stated `motivation_summary`/"5 words" from onboarding - "this connects to why you started, because you said..." - used at bigger checkpoints (weekly re-evaluation, habit transitions, Day-3 audit).
   - The agent chooses whichever lens fits the specific moment (they're not mutually exclusive and can combine), but always grounds the affirmation in something concrete and personal to this user, never a stock phrase.

### Phase 0.5 - Loom transcript-parsing spike (REVISED this round - much lighter than the old media pipeline spike) - **EXECUTED Sept 2026, ALL GATES PASSED - see `Phase-0.5-Spike-Results.md`**

### Phase 1 - LLM client abstraction (parallel with Phase 2) - **fully detailed, ready to execute**

**Decisions from this planning round**:
- **OpenAI-only for MVP** - no `AnthropicClient` implementation now. `LLMClient` is still defined as a small Protocol so a second provider is an additive drop-in later.
- **Responses API, not Chat Completions (reversed this round)** - confirmed via OpenAI's live docs (`developers.openai.com`, fetched this round after a pricing question surfaced that `gpt-4o`/`gpt-4o-mini` no longer exist as live chat models): OpenAI now explicitly recommends Responses API for all new projects, and two hard constraints rule out staying on Chat Completions for our design specifically - (1) Chat Completions does not support tool calling with `reasoning_effort` values other than `"none"` (confirmed, "Starting with GPT-5.4...") - since our tool-calling runs on every single turn, this would permanently lock us out of ever dialing up reasoning quality for the elevated tier, directly undermining the plan's own documented escalation fallback; (2) `gpt-6-astra` specifically requires the Responses API for tool calling at all. The original reasoning for picking Chat Completions ("we already own our own conversation/state management in SQLite, delegating history to OpenAI's server-side session would fight that design") turns out not to be a real tradeoff - Responses API supports the exact same self-managed, stateless, pass-full-context pattern (just `input` Items instead of `messages`, `store: false` explicitly set to avoid vendor-side statefulness, matching our own data-minimization stance from the security round). Also claims 40-80% better cache utilization than Chat Completions per OpenAI's own stated benchmarks - a further cost reduction on top of the estimate below.
- **Confirmed current models (live docs, this round) - `gpt-4o`/`gpt-4o-mini` are retired from the flagship lineup**, replaced by `gpt-6-astra` (top reasoning/coding flagship, reasoning-only - no `"none"` effort option), `gpt-5.6-sol` (flagship for complex professional work), `gpt-5.6-terra` (balances intelligence/cost), `gpt-5.6-luna` (cost-sensitive/high-volume) - all four support Functions/tool-calling and a flexible `reasoning_effort` param (`sol`/`terra`/`luna` support `"none"`, `astra` does not). **`OPENAI_MODEL` default -> `gpt-5.6-luna`** (matches old `gpt-4o-mini`'s role - cheap, fast, `reasoning_effort="none"` always, no chain-of-thought latency for routine turns), **`OPENAI_MODEL_ANALYSIS` default -> `gpt-5.6-sol`** (matches old `gpt-4o`'s stronger-tier role for the rare synthesis moments - chosen over the cheaper `gpt-5.6-terra` for genuinely stronger synthesis quality, and over `gpt-6-astra` to avoid its much higher cost while `reasoning_effort="none"` is still the default starting point even on this tier).
- **`reasoning_effort` is the real escalation dial now, not a model swap** (this is what the Responses API switch actually unlocks): both tiers default to `reasoning_effort="none"` (fast, non-reasoning, tool-calling fully supported). If Day-3 audit/weekly-re-eval/adaptive-replanning synthesis (`OPENAI_MODEL_ANALYSIS` calls only) proves too shallow in testing, the first remedy is dialing `reasoning_effort` up (`"low"` first) on the *same* `gpt-5.6-sol` call - functionally available now, whereas it was impossible under Chat Completions (see above). A full model swap (e.g. to `gpt-6-astra`) stays as the last-resort fallback beyond that, per the plan's original documented-fallback structure.
- **Canonical message/tool format = OpenAI's native Responses shapes directly** - since we're OpenAI-only, `agent_core`/`persona.py` work with plain Responses-shaped `input` Items and flat (internally-tagged) function-tool dicts throughout - no translation layer needed for MVP.
- **No streaming - reversed this round** (see top-level Decisions for the full reasoning): every `responses.create` call passes `stream=False` (the default). No `on_delta` callback anywhere in the interface - this design decision is unaffected by the separate Chat-Completions-to-Responses switch, both APIs support non-streamed calls identically for our purposes.
- **`store=False` on every call** (new, explicit this round): Responses API stores conversation state server-side by default - we explicitly disable this, since our own SQLite (`conversation_messages`/`summary_chunks`/`journal_entries`) is the single source of truth, matching the plan's existing data-minimization stance. We don't use `previous_response_id` chaining or replay reasoning items across turns - each `run_turn` call passes full context itself (recent-window + rolling summary, same design as before), and reasoning items are treated as ephemeral scratch work for that single call, never persisted.
- **Tool-loop safety cap = 7 iterations**: our own tool set per turn realistically needs <=3 calls; 7 gives headroom without allowing a runaway loop. On hitting the cap, abort gracefully, don't retry silently.

**`bot/llm/client.py`**:
- `LLMClient` - a `Protocol`/ABC with one method: `async def run_turn(input_items: list[dict], tools: list[dict], instructions: str, reasoning_effort: str = "none", model: str | None = None) -> LLMTurnResult` (`instructions` is new this round - carries the system prompt via the Responses API's dedicated top-level param rather than being prepended as a message, see `persona.py` below; `reasoning_effort` is new this round, see the escalation-dial decision above). Defaults to `config.OPENAI_MODEL` when `model` is omitted.
- `OpenAIClient(LLMClient)` - wraps `AsyncOpenAI().responses.create(model=..., instructions=instructions, input=input_items, tools=tools, reasoning={"effort": reasoning_effort}, store=False, stream=False)`. Returns either the final assistant text (via the SDK's `response.output_text` helper) or - if the `output` array contains one or more `type == "function_call"` Items - the assembled tool calls (`call_id`, `name`, parsed JSON `arguments`) directly from the single non-streamed response.
- The **tool-execution loop itself lives in `agent_core.py` (Phase 3)**, not the client: `agent_core` calls `run_turn`, and if it comes back with function-call Items, executes the matching local Python function for each, appends a `function_call_output` Item (linked to its call via `call_id`, per the Responses API's Items model - **replaces Chat Completions' `{"role":"tool","tool_call_id":...}` message shape**) to `input_items`, and calls `run_turn` again - up to the 7-iteration cap. **Reasoning-item preservation (new, confirmed via live docs this round)**: when `reasoning_effort` is escalated beyond `"none"` (the `OPENAI_MODEL_ANALYSIS` fallback path - see Model choice below), the tool loop must append the model's **entire** `response.output` array (not just the extracted `function_call` Items - reasoning Items too) into `input_items` before the next iteration, per OpenAI's own guidance ("pass back any reasoning items returned with the last function call"); at the default `reasoning_effort="none"` (both tiers, normal operation) this is a no-op since no reasoning Items are produced, so no extra code path is needed until the escalation dial is actually used. On cap exceeded: raise `ToolLoopLimitExceeded`, `agent_core` catches it, logs the incident, and sends the user a graceful fallback ("Hit a snag there - let's try that again") instead of crashing or looping forever.
- Tool schema definition: internal tools are defined once as a **flat, internally-tagged** dict - `{"type": "function", "name": ..., "description": ..., "parameters": <JSON Schema>, "strict": true}` (**Responses API shape, no nested `"function"` wrapper** - differs from Chat Completions' `{"type":"function","function": {...}}`). **`strict: true` correction this round (Issues-2.md caught a real bug)**: strict mode requires *every* property to appear in `required` - this contradicts `update_user_state`/`log_journal_entry`, which have several genuinely optional params (the whole point of `update_user_state` is calling it with one field at a time). Fix: for these two tools specifically, every param is listed in `required` but typed **nullable** (e.g. `"type": ["string", "null"]`), with `null` meaning "not provided this call" - the standard strict-mode workaround for optional fields, not a schema relaxation. `advance_stage`/`get_user_state` are unaffected (no optional params to begin with).

**`bot/llm/persona.py`**:
- `build_system_prompt(user_state: UserState) -> str` assembles, in order: (1) a condensed, static Video.md knowledge-base constant, (2) **condensed, terse imperative versions of the 9 behavioral principles** (revised - Issues.md correctly flagged that "verbatim" principles plus persona/boundary/per-stage instructions blow well past a token budget that was originally set too tight; the long prose versions above stay in *this plan document* as design rationale, the system prompt itself gets short imperative lines, e.g. "Ask why before ever offering to shrink scope. Never skip straight to a smaller version." rather than the full paragraph - **but see the raised budget below, Issues-2.md correctly pushed back on squeezing the persona itself to save a fraction of a cent per turn**), (3) persona/tone instructions, (4) the revised Principle #4 suggestion-mechanics instructions, (5) audit-day focus scoping, (6) the "only knows this one video" boundary, (7) a short, structured current-state summary injected dynamically, (8) an instruction to proactively call `log_journal_entry` the moment the user shares anything meaningful. **The resulting string is passed as the Responses API's top-level `instructions` param, not prepended into `input_items`** (see the Responses-API-switch decision above and the turn-loop note in Phase 3).
- **Audit-day focus scoping**: a per-stage dynamic instruction keyed off `state.current_stage`: `audit_day1` -> auditory-only focus; `audit_day2` -> visual-only focus, **including an instruction to share the user's own Loom link back to them** (revised this round - replaces the old Telegram reply-quote design now that the recording lives on Loom, not in Telegram chat history; the user rewatches via Loom's own player, muted, which has genuinely better playback controls than scrolling back through Telegram); `audit_day3` -> synthesis day, exempt from isolation. Also covers the 24-hour-rule time gate's explanation.
- **The lifelong-Kaizen reveal**, gated by `state.kaizen_reveal_shown` - unchanged from prior rounds, **now also the delivery point for the new habit-transition comparison artifact** (baseline vs latest metrics + the user's own 5-words callback - see Phase 3's habit-transition note).
- **Context-bloat guardrail, budget raised this round**: keep the static portion of the system prompt compact (target under **~2500 tokens**, raised from the previous ~1500 - Issues-2.md correctly pointed out that the persona *is* the deliverable ("should not feel like a computer"), and squeezing it to save roughly $0.0002/turn on a mini model was optimizing the wrong thing; the terse-imperative rewrite from the persona.py note above stays as a good discipline regardless, it's just no longer stretched to hit an artificially tight ceiling - **verify this empirically via `tiktoken` in a unit test, not by manual inspection**, per Issues.md's original critique of "manually confirm" as insufficient), inject only a short state summary, not a full journal dump.
- **Recent conversation window = rolling summary buffer, not a hard cutoff** (unchanged from prior rounds). **Confirmed this round (Issues-2.md asked)**: the folding/compaction logic operates uniformly over `conversation_messages` rows and never assumed a `'tool'`/`'system'`-role row could exist there - it was already only ever written by `append_conversation_message` for final `user`/`assistant` text (tool-call plumbing was always ephemeral, per-turn only, never persisted) - so the `role` CHECK narrowing (Phase 2) required no change to this folding logic itself.
- **Prompt-caching-aware compaction design** (unchanged from prior rounds - message ordering, append-only summary chunks, `prompt_cache_key` per user, no volatile content in the static block, batch compaction on a fixed cadence).

**Telegram reply bridge (interface decided now, implemented in Phase 3) - replaces the prior streaming design**:
- `agent_core` calls `send_typing_action` (repeating every ~4s, since Telegram's typing indicator expires after ~5s) while `run_turn`'s tool loop executes.
- Once the final assistant text is ready, send it as one complete message via `reply_text`/`send_message` - no progressive editing. For longer replies, `agent_core` may split into two short, natural bubbles with a brief (~0.5-1s) delay between them for more human pacing, at its own discretion (not a hard rule).

**Model choice**: `OPENAI_MODEL` default `gpt-5.6-luna` with `reasoning_effort="none"` (cost-effective, confirmed via live pricing/model docs this round - see Decisions above; overridable). Chosen over dialing up reasoning effort for routine turns because higher `reasoning_effort` values add several-seconds-per-turn latency which directly undermines the "should feel like texting a person, not a computer" requirement, and are less steerable for warm/Socratic persona tuning. **Documented fallback chain (now genuinely available thanks to the Responses API switch, refined this round with two further confirmed rungs)**: if Day-3 audit pattern-detection proves too shallow in testing, escalate `OPENAI_MODEL_ANALYSIS` calls specifically, in order: (1) dial `reasoning_effort` up (`"low"` first, then `"medium"`) on the same `gpt-5.6-sol` call path; (2) if still insufficient, set `reasoning.mode="pro"` (confirmed via live docs - GPT-5.6 models support `standard`/`pro` reasoning modes, `pro` does more model work at the same per-token rates, for difficult tasks that can tolerate higher latency/cost); (3) only as a last resort, a full model swap to `gpt-6-astra`. **Safeguard**: if `reasoning_effort` is ever escalated beyond `"none"`, also set an explicit `max_output_tokens` (per OpenAI's own guidance - reasoning tokens are billed as output tokens and can silently run long) rather than leaving it unbounded.

**Model routing (two-tier, per-call override)**: `OPENAI_MODEL_ANALYSIS` default `gpt-5.6-sol` (confirmed via live docs this round - see Decisions above) for the low-frequency, high-stakes synthesis moments: (1) Day-3 audit -> habit-suggestion synthesis, (2) weekly re-evaluation synthesis, (3) adaptive-replanning-option generation after missed days. Every other turn stays on `OPENAI_MODEL` (`gpt-5.6-luna`). Both tiers default to `reasoning_effort="none"`; only `OPENAI_MODEL_ANALYSIS` calls have a documented path to dial it up if needed (see Model choice above).

### Phase 2 - Data model & persistence (parallel with Phase 1) - **fully detailed, ready to execute**

**Decisions from this planning round** (mostly unchanged from prior rounds; new items called out):
- **`aiosqlite`, not plain `sqlite3`** - PTB/our bot is fully async.
- **Single shared connection for the process lifetime** - opened in PTB's `post_init`, stored on `application.bot_data["db"]`, closed in `post_shutdown`.
- **`PRAGMA journal_mode=WAL` + `PRAGMA foreign_keys=ON` + `PRAGMA busy_timeout=5000`** on connection open.
- **Idempotency guards against double-processing** - `UNIQUE(user_id, telegram_file_id)` + `INSERT OR IGNORE` on `media_refs`; same for `missed_days` (`UNIQUE(user_id, day)`) and the new `daily_engagement` table below.
- **Boolean coercion note**: `journal_entries.completed` is `INTEGER` (0/1/NULL) - explicit coercion needed on read/write.
- **Atomicity for multi-table operations**: `wipe_user`/`reset_user_progress` wrapped in explicit transactions.
- **Test strategy**: pytest fixtures use `:memory:` SQLite. **New this round**: also add **scripted conversational test scenarios against a mocked `LLMClient`** (Issues.md flagged persona verification as entirely manual/eyeballed) - at minimum three scenarios: (a) user misses two days in a row - assert the agent's mocked exchange asks *why* before ever offering to shrink scope; (b) user pushes back on an observed pattern - assert the agent drops it rather than insisting; (c) a full onboarding->recording->habit-selection happy path exercises every tool call in the expected order. These mock `LLMClient.run_turn` to return scripted responses/tool-calls and assert on `agent_core`'s resulting tool invocations and DB state, not on real model output.
- **No formal migration framework** - `schema.sql` uses idempotent `CREATE TABLE IF NOT EXISTS`.
- **Timestamps as ISO8601 TEXT** (UTC), not integers.
- **`/reset` semantics**: resets `state` back to defaults, resets `users.simulated_day` to 0 and `users.day_zero_at` to a fresh `datetime('now')`, and **increments `users.epoch`** (new this round - see below, fixes a day-number-collision bug), but **keeps** `journal_entries`/`media_refs`/`conversation_messages`/`summary_chunks`/`daily_engagement`/`missed_days` history intact, now correctly disambiguated from the new run via the epoch column.
- **Metrics are always computed deterministically in code, never asked of the LLM**.
- **Canonical day resolver - new columns this round** (fixes the real bug Issues.md caught: `simulated_day` never advanced for a real, non-demo user): `users.simulated_day` is **redefined from "the current day" to a manually-added offset**, defaulting to 0, bumped only by `/advance N` (`simulated_day += N`, never decremented, never reset except by `/reset`). New column **`users.day_zero_at TEXT NOT NULL DEFAULT (datetime('now'))`**, stamped immediately at user-row creation (the same moment as `created_at`), never onboarding completion - **fixes a real bug Issues-2.md caught**: the earlier "stamp at onboarding completion" design meant `day_zero_at` was NULL for the entire onboarding conversation, and `get_effective_day()` would be called against that NULL the moment `record_daily_engagement` fires on the very first onboarding message (before onboarding ever completes) - a NULL-arithmetic bug on day one of every user's journey. Stamping at row creation via a SQL-level `NOT NULL DEFAULT` eliminates the NULL case entirely rather than special-casing it in application code. `/reset` re-stamps this to a fresh `datetime('now')` (not back to NULL, which the column no longer permits) as part of starting a new epoch (see below). See Phase 4 for the `get_effective_day()` helper that combines these into the one source of truth for "what day is it for this user" everywhere in the codebase.
- **New `users.timezone TEXT` column** (IANA name, e.g. `"Asia/Kolkata"`) - captured via one onboarding question (see Phase 3), used by Phase 4's daily sweep to nudge each user at their own local hour rather than a single server-local hour for everyone.
- **New `daily_engagement` table** (supports the redefined missed-day logic): `UNIQUE(user_id, epoch, day)`, one row per user per effective-day they sent any message - populated via `INSERT OR IGNORE` in `handlers.py`'s text/voice/video handlers (the same place `users.last_message_at` is already updated), keyed on `get_effective_day(user_row)`. Missed-day detection (Phase 4) now checks "does a row exist for `day-1`" instead of checking exercise-completion.
- **`users.epoch` column - fixes a `/reset` bug where old and new runs' day numbers collide** (Issues-2.md caught this): since `day` is now derived from `day_zero_at`+`simulated_day` rather than stored directly, a second run after `/reset` reuses the same day numbers (0, 1, 2...) as the first run - but `journal_entries`/`entry_metrics`/`daily_engagement`/`missed_days` history is deliberately *kept*, not wiped, on `/reset`. Without a way to tell which run a given day-numbered row belongs to, `get_metric_trend`/`get_baseline_and_latest_metrics` (ordered by day) and the missed-day/engagement checks (keyed on `(user_id, day)` uniqueness) would silently interleave or collide with the prior run's rows. Fix: new `users.epoch INTEGER NOT NULL DEFAULT 0`, incremented by `/reset` (never by `/wipe`, which deletes everything outright and has no collision risk). `journal_entries` gains an `epoch` column (stamped from the user's current epoch at write time); `daily_engagement` and `missed_days` gain an `epoch` column and their `UNIQUE` constraints become `UNIQUE(user_id, epoch, day)` instead of `UNIQUE(user_id, day)`. Every day-scoped read (`get_metric_trend`, `get_baseline_and_latest_metrics`, `has_engagement_on_day`, missed-day counts) filters by the user's *current* epoch in addition to `user_id`.
- **`users.last_sweep_day` column - backs the hourly sweep's dedup, which previously wasn't stored anywhere** (Issues-2.md caught this): the hourly sweep's "hasn't already been processed for this effective day" check needs somewhere to actually record that fact - without it, a process restart within the same matching local hour could re-run `run_daily_checks_for_user` and double-nudge. New `users.last_sweep_day INTEGER`, set unconditionally via `repo.record_sweep_run(user_id, day)` every time `run_daily_checks_for_user` actually executes for that user (regardless of which reason, if any, it returns) - not just when the daily check-in branch fires. The hourly sweep's dedup check becomes simply `users.last_sweep_day != get_effective_day(user_row)` before calling the helper at all.

  0. **Early-stage re-engagement nudge** (new this round - see Phase 4 decisions above): if `state.current_stage` is one of `{onboarding, initial_recording, audit_day1, audit_day2, audit_day3, habit_selection}`, `day >= 1`, `repo.has_engagement_on_day(user_id, day - 1)` is false, and `state.reengagement_nudge_count < 3` - increment `state.reengagement_nudge_count` and return `'reengagement_nudge'` (a one-day fuse, shorter than step 1's two-day threshold; capped at 3 consecutive fires, reset to 0 on the user's next real engagement).
  1. **Missed-day detection** (revised this round): only if `state.current_stage == 'weekly_cycle'` and `day - 1 > state.weekly_cycle_started_effective_day`; check `repo.has_engagement_on_day(user_id, day - 1)` - if false, call `flag_missed_day(user_id, day - 1)`.
  2. **Missed-day nudge**: unchanged - if unresolved `missed_days` count >= 2 and `state.adaptive_nudge_sent == 0`, set the flag and return `'missed_day_nudge'`.
  3. **Weekly re-eval prompt**: unchanged - `is_weekly_reeval_due(user_id)`.
  4. **Daily check-in**: unchanged - `state.current_stage == 'weekly_cycle'` and not already sent today and no organic message today.
  5. Else return `None`.

**`bot/handlers.py` addition - `/advance [N]`** (unchanged edge-case handling from prior rounds - input validation, passcode gate, batching fix collecting all reasons into one `initiate_conversation` call, 24h-gate inline check, `last_message_at`/`daily_engagement` never touched by admin commands - **new this round**: `/advance` bumps `users.simulated_day` by `N` total (the offset), and the loop's internal "day" value at each iteration is `get_effective_day(user_row)` recomputed after each bump, rather than a raw absolute increment). **Reason-list dedup added this round (Issues-2.md caught this)**: since step 0's `reengagement_nudge` can now legitimately fire on multiple consecutive days within one `/advance N` jump (up to its cap of 3) before the counter stops it, the collected-reasons list is **deduplicated (preserving order) before being passed to `initiate_conversation`** - without this, `/advance 5` on a silent onboarding user would collect several identical `'reengagement_nudge'` entries into one batch, which would read as bizarre/repetitive to the LLM composing the single consolidated message.

### Phase 5 - Media analysis (Loom-transcript parsing in MVP; full analysis stubbed for later) - **fully detailed, ready to execute**

**Decisions from this planning round** (complete rewrite - Loom link + pasted transcript replaces the local Bot API server + ffmpeg + Whisper video pipeline entirely):
- **Primary path needs no download, no ffmpeg, no per-submission ASR call at all**: the initial recording and every weekly check-in are a Loom share link plus a pasted/uploaded transcript (and optional summary), stored via `media_refs(kind='loom')` with `loom_url`/`loom_duration_seconds`. Day 2's visual self-report points the user back to their own Loom link (Loom's player, muted) rather than reply-quoting a Telegram video message - the bot never downloads or processes video frames itself in MVP.
- **`bot/analysis/loom.py`** (new primary module, replaces `transcription.py`): (1) fetches oEmbed metadata (`https://www.loom.com/v1/oembed?url=<share_url>`) for `duration`/`title`/`thumbnail` - a plain HTTPS GET, no auth, no local server; **requires the user's Loom link to be set to "anyone with the link" (see Phase 3's explicit onboarding step) - a restricted link won't resolve**; (2) parses the user-pasted transcript into `(timestamp, text)` paragraph segments via a regex covering the timestamp formats confirmed in Phase 0.5's spike; (3) computes `filler_word_count`/`filler_rate` (regex word-list match against the raw transcript text), `words_per_minute` (total word count / duration), `repetition_count` (adjacent-word/phrase repeats in the text) - **these five metrics never need timestamps at all**, they compute from text + duration alone; (4) **fail-soft pause estimation, using an articulation rate (math corrected this round - see the top-level Decisions fix)**: computes each paragraph's own `words_i / duration_i`, takes the **85th percentile across all paragraphs** as the self-calibrated "unpaused pace" baseline (falls back to a ~150 wpm literature constant if fewer than ~5 paragraphs), then estimates `long_pause_count`/`longest_pause_seconds` as `gap_i - (words_i / articulation_rate)` against that baseline - not the overall (pause-inclusive) WPM, which would mathematically cancel out any real pause signal; if the timestamp format isn't recognized, the two pause-metric `entry_metrics` rows are simply omitted (never a misleading `0`) while the other five still write normally, and **the agent tells the user transparently** ("couldn't estimate pauses from what you pasted, everything else came through fine") per the "always show the mirror honestly" principle. (5) **oEmbed-duration fallback (new this round - review caught this had no stated Plan B)**: if oEmbed fails to return `duration` (restricted link, transient error, or any other cause), estimate duration instead from the transcript's own last paragraph timestamp plus an estimate of that final paragraph's spoken length, using the same articulation-rate baseline - `duration_seconds`/`words_per_minute` still compute, just from this fallback estimate rather than oEmbed's authoritative figure, and the agent notes this transparently too.
- **Loom's optional AI summary is stored but never used for metrics**: if provided, folded into the LLM's context as supplementary qualitative signal only (see Phase 3); absence never blocks progress.
- **Fallback path - user's choice each time Loom fails or the transcript is insufficient, not a fixed mode** (see Phase 3's fallback-flow bullet): the agent offers a Telegram voice-message alternative and explicitly asks the user to pick:
  - **`self_report`**: no transcription, no computed metrics for that entry - `bot/handlers.py` records the media ref (`fallback_mode='self_report'`) and hands straight off to a normal reflective conversation via `agent_core`, logged as a qualitative `journal_entries(type='reflection')` row. Zero new infrastructure, zero ASR call.
  - **`full_metrics`**: `bot/analysis/voice_fallback.py` (new, narrow module) downloads the small voice note via the standard cloud Bot API (well under 20MB, no local server needed) -> **if the OGG/Opus container isn't directly accepted by the transcription API** (OpenAI's supported formats are `mp3, mp4, mpeg, mpga, m4a, wav, webm` - no `ogg`), runs a single lightweight `ffmpeg` format-conversion call (not the old video-extraction pipeline) -> calls `client.audio.transcriptions.create(model=config.OPENAI_TRANSCRIBE_MODEL, response_format="verbose_json", timestamp_granularities=["word"])` -> computes the same seven metrics as the Loom path (this branch *can* get exact word-level pause detection, unlike the Loom-estimate path, since real ASR timestamps are available) -> writes via `record_entry_metrics`. This reintroduces the `whisper-1` deprecation risk (Aug 2026 deprecated, Feb 2027 shutdown) and per-minute cost, but scoped to rare fallback occurrences only, not every submission - see Further Considerations for the updated cost impact.
- **Transcription/parsing failure handling**: for the Loom path, a genuinely unparseable transcript (e.g. empty paste, wrong content entirely) triggers a short, fixed, non-LLM-composed message asking the user to double-check what they pasted, distinct from the softer "pause estimation unavailable" case above, which still proceeds; `media_refs` row left as `processed=0` until something usable arrives. For the `full_metrics` fallback branch, unchanged from the old design: a short fixed message asking the user to resend or switch to `self_report`.
- **Duration reconciliation**: use Loom's own oEmbed `duration` for the primary path; use the ASR response's own `duration` for the `full_metrics` fallback branch.
- **Provider-agnostic normalized shape retained across both paths**: both `bot/analysis/loom.py` and `bot/analysis/voice_fallback.py` return the same `(transcript_text, segment_or_word_timestamps, duration_seconds)` shape to the shared metric-computation functions, which don't care whether timestamps are Loom's coarser paragraph-level estimates or the fallback ASR's exact word-level ones - this keeps the seven-metric computation code single-sourced rather than duplicated per path.

**`bot/analysis/base.py`**: abstract `MediaAnalyzer.analyze(...) -> AnalysisResult` - unchanged, kept as a small Protocol/ABC that both `loom.py` and `voice_fallback.py` implement.

- **Explicit scope boundary** (unchanged from prior rounds): true stuttering-specific behaviors (prolongations, blocks) are within-word phenomena requiring audio signal analysis, explicitly left to the stubbed `full_analysis.py`.
- **Ethical framing tie-back to Principle 8** (unchanged): these metrics are surfaced only as neutral, factual observations - the agent never asserts a fluency-disorder label.

`bot/analysis/full_analysis.py`: stub only (interface + TODO) for future audio/visual signal heuristics - noted as an open possibility, not designed now. **Note this round**: since the bot no longer holds a copy of the video at all (Loom hosts it), a future vision-capable-model pass over frames would need its own, separate Loom-video-download step - genuinely harder to add later than under the old local-server design, a real tradeoff of this pivot (see Further Considerations).

12. **`whisper-1` deprecation - now a much smaller-stakes risk, scoped to the rare fallback branch only**: still deprecated Aug 26, 2026, shutdown Feb 26, 2027 - but since it's no longer on the critical path for every submission, a shutdown before this branch is ever revisited would only affect the rare fallback case, not the core product. **Open end deliberately kept**: `bot/analysis/voice_fallback.py`'s interface returns the same normalized `(transcript_text, word_timestamps, duration_seconds)` shape regardless of provider, so switching to Deepgram/AssemblyAI later touches only that one module's internals.
13. **Loom account/tier dependency (new this round)**: the user (and, implicitly, end-users of a real deployment) needs a Loom account; the free Starter tier caps screen recordings at 5 minutes, so the 20-minute "advanced" initial-recording option requires a paid Business account. This is a genuine new external dependency the old Telegram-only design didn't have - worth surfacing explicitly to Samyak as part of the judgment-call writeup, alongside the infrastructure/cost/risk it removes in exchange.
14. **Parse fragility (new this round)**: Loom's copy-paste timestamp format may differ across desktop vs mobile, and across transcript languages - the parser is designed to fail soft (skip pause metrics, keep the rest, tell the user transparently) rather than break the pipeline, but this remains a real, ongoing maintenance surface that a pure-ASR design wouldn't have had, since Loom's copy-paste behavior isn't a documented, versioned API contract.
15. **SHELVED (researched, client decision - Sept 2026): Desert Ant's "Uhm" on-device filler detector** (https://desertant.com/models/uhm/) - acoustic filler detection straight off the waveform, no transcript step, 20ms precision, ~45-51MB model, free up to 100k monthly active devices. Evaluated as a potential upgrade over our text-count-based filler metrics. **Why it does not fit today**: (a) our primary path is text-only by design (the Loom pivot - no audio ever reaches the bot, so there is no hook for an acoustic model); (b) the SDK is Swift-only right now (Android/Kotlin/JS "coming soon"), so it cannot run inside our Python bot except via the 51MB ONNX server build, which would add a model runtime to a POC whose cost story is "$0.56/user/month, no per-minute audio charges"; (c) the only in-architecture seam is the rare voice-fallback "full metrics" branch, which should almost never fire - not worth the runtime for that. **When to revisit**: when the `full_analysis` stub (pitch/pace/eye-contact) is eventually built and the project first accepts real audio again (the opt-in Loom re-upload from item 2 above) - at that point a `UhmAnalyzer` implementing the existing `MediaAnalyzer` provider-neutral interface in `bot/analysis/base.py` is a same-shape drop-in (same class of seam as the Deepgram/AssemblyAI option in item 12), and would also fix the known ASR weakness that transcribers can omit fillers from output (our own Phase 0.5 spike confirmed uhm/uh sounds survive Loom's ASR, but omission is a documented failure mode of Whisper-style transcribers generally). Their "speaking coach" use case on-device (count fillers across sessions, private, no upload) is a suggestive future companion-app direction if the project ever grows beyond Telegram.
